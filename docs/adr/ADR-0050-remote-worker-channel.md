# ADR-0050: Remote-worker channel over GhostPort

- Status: Accepted
- Date: 2026-09-24
- Milestone: P4-M007

## Context

Workers must be able to run tasks from other machines. Until now every AgentForge listener has
been loopback-only, and the core has no cryptographic code. We control a tool that already solves
authenticated, encrypted transport: GhostPort. It provides Noise KK with pinned keys,
client-dials-server connections (so NAT is not a problem), and per-peer link restrictions. It is
built on tokio and snow.

## Decision

- **GhostPort is the network layer, as a separate process.**
  - The coordinator runs a GhostPort server. Each worker host is a pinned `[[peers]]` entry,
    restricted to its own forward link.
  - The link targets `forged`'s worker API on a loopback port.
  - The worker host's GhostPort client listens on its own loopback port.
  - AgentForge links no crypto, gains no dependencies, and still binds only loopback. The worker
    API refuses a non-loopback `bind`, and the client refuses a non-loopback endpoint, so the
    plaintext protocol cannot be pointed at a network by mistake.
- **Two authentication layers.**
  - GhostPort authenticates the machine: without the pinned key, the Noise handshake cannot
    complete.
  - AgentForge authenticates the worker: every request carries the worker ID and its 256-bit
    secret.
  - Secrets are generated by `forge worker enroll` from the OS CSPRNG and kept in
    `.forge/workers/<id>.secret` (mode 600; group- or other-readable files are refused). They are
    compared in constant time.
  - A tunnel from one worker's host therefore still cannot act as another worker.
- **The AFW1 protocol.** One bounded line per request, one request per connection, served by a
  loopback listener in `forged` configured by `.forge/worker-api.conf` (off by default).
  - `CLAIM` returns the next claimable lease (the P4-M005 rule), the coordinator's exact `HEAD` as
    the base commit, and the task contract. `RENEW` and `RELEASE` act only on the caller's own
    leases.
  - Actions are audited as `worker:<id>` with `channel=remote`, and claims also record
    `base_commit`.
  - A failed authentication gets a generic `unauthorized` after a fixed delay. It is logged to
    stderr only, so it cannot flood the audit chain.
- **The contract travels as the existing `agentforge-task-prompt-v1` document.** It is exactly
  what a local agent receives, and the new strict `parse_task_prompt` decodes it on the worker side.
- **Expiry uses the coordinator's clock only**, so clock skew between hosts cannot extend a lease.

## Verification

This was checked with real GhostPort processes (v0.1.1), as recorded in the P4-M007 plan:
- claim, renew, and release through the tunnel;
- an unpinned GhostPort key was rejected (`no configured peer matched`);
- a wrong AgentForge secret through a valid tunnel was refused;
- a recording relay on the tunnel's data path captured 1,473 bytes containing none of the protocol
  verbs, the secret, the contract, or the IDs.

## Consequences

Positive:

- workers can hold and manage leases from anywhere with outbound connectivity to the coordinator;
- the security-critical code is GhostPort's audited Noise path, not new code in AgentForge.

Negative:

- operators run and configure GhostPort alongside `forged` (a verified recipe is in
  `REMOTE_WORKERS.md`);
- worker secrets are stored in plaintext files on the coordinator, protected by file mode like SSH
  keys. Hashing them would need a hash implementation that AgentForge does not have.

## Alternatives considered

- **Link GhostPort-core into `forged`.** Rejected: it would pull tokio and snow into the daemon and
  make AgentForge listen on the network itself.
- **Plain TLS in AgentForge.** Rejected: it needs crypto dependencies and certificate management,
  and duplicates GhostPort.
- **Identify workers by GhostPort link alone.** Rejected: that is a single layer, and one shared
  target port cannot tell workers apart.
